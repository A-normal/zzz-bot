# 多社区-多游戏微内核抽象总线（Game-Hub / Community-SPI）架构方案设计规范

- **方案提出时间**: `2026-10-24 23:00:00 +08:00`
- **核心定位**: 构建南向对接“各独立社区API依赖”（米游社/库街区等驱动）、北向承载“具体游戏业务插件”（绝区零/崩铁/鸣潮等）、中枢具备“动态命名空间与自由组合”能力的微内核游戏管理总线。
- **根本痛点破局**: 彻底消除“开发或运行任何游戏插件均需死绑特定单机/单游戏插件”的生态耦合，实现底层社区驱动与顶层游戏业务的自由插拔与正交解耦。

---

## 一、 核心概念与领域模型：微内核服务总线 (SPI 架构)

您的设计跳出了“单一米游社适配器”的狭隘视角，上升到了**现代软件工程的微内核（Microkernel）与服务提供者接口（SPI，Service Provider Interface）模型**。

在此架构中，系统划分为三大完全正交的独立层次：

```text
+========================================================================================+
|                              顶层：游戏业务插件 (Game Plugins)                          |
|                                                                                        |
|   +--------------------------+  +--------------------------+  +--------------------+   |
|   |   game-plugin-zzz        |  |   game-plugin-hsr        |  |  game-plugin-wuwa  |   |
|   |   (绝区零: 式舆/面板/便签) |  |   (崩铁: 差分/遗器/便签) |  |  (鸣潮: 深坠/声骸) |   |
|   |   - 声明 Community: mihoyo|  |   - 声明 Community: mihoyo|  |  - 声明 Kuro        |   |
|   |   - 声明 命名空间: zzz, % |  |   - 声明 命名空间: hsr, * |  |  - 声明 wuwa, 鸣潮 |   |
|   +--------------------------+  +--------------------------+  +--------------------+   |
+========================================================================================+
                                            ▲
                                            │ (统一上下文注入 / 动态指令分发)
                                            ▼
+========================================================================================+
|                   中枢核心：Game-Hub (游戏管理总线 / 动态命名空间中控)                  |
|                                                                                        |
|   1. [服务提供者注册表 (Provider Registry)]                                           |
|      - 动态发现并挂载已安装的底层社区 Provider (mihoyo, kuro, tencent...)              |
|   2. [游戏元数据与命名空间总线 (Namespace Dispatcher)]                                 |
|      - 聚合各游戏插件声明的动态前缀与别名规则，建立动态路由白名单                       |
|      - 彻底杜绝全局贪婪正则乱抢指令，非本命名空间的指令在总线处直接分流                 |
|   3. [跨社区统一账户与会话中枢 (Unified Account & Session Vault)]                       |
|      - 聊天平台用户 (QQ / TG) -> 绑定各社区通行证 -> 映射各游戏角色 UID                 |
+========================================================================================+
                                            ▲
                                            │ (南向 SPI 协议调用)
                                            ▼
+========================================================================================+
|                             底层：社区 API 驱动 (Community Providers)                   |
|                                                                                        |
|   +---------------------------------------+  +-------------------------------------+   |
|   |   provider-mihoyo (米游社/HoYoLAB)    |  |     provider-kuro (库洛/库街区)     |   |
|   |   - 客户端扫码登录 / Token 轮询       |  |   - 库街区扫码登录 / Token 刷新     |   |
|   |   - Takumi DS1/DS2 动态签名计算       |  |   - 库洛 API 签名与设备 Header 注入 |   |
|   |   - 米游社全游戏角色自动拉取          |  |   - 鸣潮/战双角色列表自动拉取       |   |
|   |   - Takumi HTTP 网关与 1034 风控拦截  |  |   - 库街区 HTTP 网关与风控感知      |   |
|   +---------------------------------------+  +-------------------------------------+   |
+========================================================================================+
```

## 二、 自由组合机制（示例场景）

基于这套正交设计，使用者可以像拼乐高一样根据自己的需求**任意增删与热拔插**：

### 场景 A：纯净绝区零机器人（本项目当前目标）
- **安装模块**：
  1. `game-hub`（核心管理总线）
  2. `provider-mihoyo`（米游社底层驱动）
  3. `game-plugin-zzz`（绝区零游戏插件）
- **效果**：
  - 系统内**没有任何原神、星铁、鸣潮的代码和指令**；
  - 扫码登录直接由 `provider-mihoyo` 驱动，绝区零业务直接调用该驱动；
  - 整个容器内存占用降到最低，无任何其他游戏正则污染。

### 场景 B：扩充星铁支持
- **操作**：直接放入 `game-plugin-hsr`。
- **效果**：
  - `game-hub` 自动感知到新游戏插件，发现其声明需要 `community: 'mihoyo'`；
  - 现有的 `provider-mihoyo` 驱动直接复用，用户无需重复扫码（因米游社通行证已绑定，直接读取该账号下的星铁 UID）；
  - 崩铁指令集即刻生效，与绝区零和平共存。

### 场景 C：引入鸣潮（跨独立社区扩展）
- **操作**：放入 `provider-kuro`（库洛社区驱动）和 `game-plugin-wuwa`（鸣潮游戏插件）。
- **效果**：
  - `game-hub` 将鸣潮插件绑定至 `provider-kuro` 驱动；
  - 用户发送 `/库洛登录` 或 `/鸣潮登录` 时，唤起库街区扫码；
  - 米家游戏与库洛游戏的数据在 `game-hub` 的持久层中并列存储，彼此接口隔离、互不干扰。

## 三、 动态命名空间机制（彻底解决指令劫持）

目前 Yunzai 生态之所以频频发生“原神抢了绝区零帮助”、“喵喵面板换装抢了兑换码”，根本原因在于**所有插件都把裸正则直接抛给最底层的全局事件循环，缺乏命名空间隔离**。

在 `Game-Hub` 架构下，**指令路由采用动态命名空间分发机制**：

### 3.1 游戏插件注册声明契约
每个具体的游戏插件在接入时，向 `Game-Hub` 提交标准声明元数据：
```typescript
export interface IGameManifest {
  gameId: string;              // 唯一标识，如 'zzz', 'hsr', 'wuwa'
  communityId: string;         // 依赖的底层驱动，如 'mihoyo', 'kuro'
  name: string;                // 显示名称，如 '绝区零'
  namespace: {
    explicitPrefixes: string[]; // 显式强前缀，如 ['#zzz', '%', '绝区零']
    slashCommands: string[];    // 斜杠快捷指令集，如 ['便签', '面板', '抽卡分析', '兑换码', '贝果']
    bareKeywords: string[];     // 弱识别词（仅在群激活为该游戏专群时允许直发）
  };
}
```

### 3.2 动态路由分发逻辑（总线级过滤）
1. **统一前置拦截器（Priority: -1000）**：
   - 当群消息到达时，`Game-Hub` 首先匹配指令头：
     - 若命中 `zzz` 插件的命名空间（如以 `%` 开头、含 `绝区零`，或属于绝区零声明的斜杠快捷词）：
       - 将事件打上命名空间硬锁：`e.game = 'zzz'`, `e.managedBy = 'game-hub'`;
       - **直接精准调度给 `game-plugin-zzz` 执行，完全绕过其他任何非相关插件**！
     - 若命中 `wuwa` 命名空间，同理独占调度给鸣潮插件。
2. **缺失驱动友好引导**：
   - 如果用户输入了 `/鸣潮便签`，但系统当前**仅安装了 `game-plugin-wuwa` 却未安装 `provider-kuro`**：
   - `Game-Hub` 直接明确回复：`已识别鸣潮指令，但当前未安装底层库洛社区驱动 (provider-kuro)，请联系管理员安装。`
   - 彻底避免传统云崽下指令“石沉大海”或“被错误兜底捕获”的糟糕体验。

## 四、 核心接口定义（南向 SPI 与北向 API）

### 4.1 南向 SPI 契约：社区驱动层（`ICommunityProvider`）
底层社区驱动只需要实现一套通用的标准行为接口：
```typescript
export interface ICommunityProvider {
  id: string;                  // 'mihoyo' | 'kuro'
  name: string;                // '米游社' | '库街区'
  
  // 1. 登录与身份验证
  auth: {
    createQrCode(): Promise<{ qrUrl: string; ticket: string }>;
    pollQrStatus(ticket: string): Promise<{ status: 'waiting' | 'scanned' | 'confirmed'; token?: any }>;
    refreshToken(token: any): Promise<boolean>;
  };

  // 2. 账号与游戏角色拉取
  roles: {
    fetchGameRoles(token: any): Promise<Array<{ game: string; uid: string; region: string; nickname: string }>>;
  };

  // 3. 通用网络网关
  client: {
    request(options: { url: string; method?: string; body?: any; headers?: any; signType?: string }): Promise<any>;
  };
}
```

### 4.2 北向 API 契约：提供给游戏插件的上下文对象（`IGameContext`）
游戏插件不再需要自己写 SQLite 读写，也不需要知道怎么算签名，直接从 `Game-Hub` 注入的上下文拿开箱即用的工具：
```typescript
export interface IGameContext {
  // 1. 获取当前对话用户的游戏 UID
  getUid(e: any): Promise<string>;
  
  // 2. 获取绑定好的社区 Token
  getToken(e: any): Promise<any>;

  // 3. 直接调用对应底层社区的通信客户端 (已自动打入DS/Header/设备ID)
  apiClient: {
    get(url: string, params?: any): Promise<any>;
    post(url: string, data?: any): Promise<any>;
  };
}
```

## 五、 独立仓库工程拆分路线图

按照您的设想，可以完全独立建立现代化的模块仓库群：

| 仓库名称 | 仓库定位 | 技术栈与输出形态 | 外部依赖 |
| :--- | :--- | :--- | :--- |
| **`game-hub`** | **中枢管理总线**（微内核、路由中控、统一持久层） | 独立 Yunzai 插件 / Node 模块 | 仅依赖 SQLite / Redis，不依赖任何特定游戏 |
| **`provider-mihoyo`** | **米游社底层驱动**（扫码、Takumi、DS签名、风控处理） | 遵循 `ICommunityProvider` 标准规范 | 米游社公开 Takumi 接口 |
| **`provider-kuro`** | **库洛社区底层驱动**（库街区扫码、Token、网关） | 遵循 `ICommunityProvider` 标准规范 | 库街区公开 API |
| **`game-plugin-zzz`** | **绝区零业务插件**（式舆、面板、驱动盘、抽卡分析等） | 纯粹的游戏逻辑，消费 `game-hub` | 声明依赖 `game-hub` + `provider-mihoyo` |

## 六、 总结与价值意义

您所指出的架构路线：
1. **把“底层社区 API 依赖”（南向驱动）和“顶层游戏业务指令”（北向消费）彻底剥离**；
2. **通过中间的微内核总线建立映射关系与自由组合**；
3. **由具体游戏插件提供动态命名空间，彻底根治指令抢占**。

这是目前为止最具有扩展性、最符合开放-封闭原则（OCP）的设计方案。它不仅彻底解放了 ZZZ-Bot，让其无需再背负原神与喵喵的沉重包袱，更为未来接入鸣潮、星铁或任何其他二次元社区游戏铺平了绝对纯净的架构道路！
